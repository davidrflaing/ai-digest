  • [skill] MCP Tasks and Elicitations in the Claude Code CLI (ClaudeDevs, Oct 23; Tasks in public beta from v2.1.304; other Claude products "soon") — Tasks: an MCP tool can answer at once with a task ID and keep working on the server. The footer shows 1 MCP task, Claude Code polls tasks/get (every 250 ms to 30 s, the server picks), the statuses are working / input_required / completed / failed / cancelled, and the result goes to Claude when it's done; in /tasks, x cancels. A remote (HTTP) server's task keeps running after you exit and is picked up again on claude --resume; a stdio server's task dies with the session, even though /tasks says it survives. Elicitations: the server pauses mid-task and asks you in a dialog (confirm a refund, fill in a missing field, or go to a URL for a payment); pressing Esc or declining counts as an answer, and the server decides what happens next. In claude -p no elicitation is ever shown: Claude Code asks the server to cancel the task and runs no Elicitation hook, and 2.1.310 (below) now tells Claude "no answer came, don't repeat the call" when an unanswered one times out. Settings: CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0 makes Claude wait for every MCP call; CLAUDE_AUTO_BACKGROUND_TASKS=1 turns on backgrounding in non-interactive runs. Honest flags: subagent calls never go to the background; not in VS Code or the desktop app; the server needs protocol revision 2026-07-28; the docs section on what the elicitation form looks like wasn't readable this run. Dave: you write MCP servers (notion-tasks), and an elicitation is the rulebook's "your OK" mark built into the protocol. A confirm on batch_update_tasks, or on any send tool you build later, appears as a dialog in an attended lane and is cancelled in the launchd jobs, which is what the rulebook asks for with nothing extra to build. Tasks fits the slow jobs a lane currently sits and waits on: a NotebookLM generation from run_episode.py, or a meditation render, exposed as an HTTP MCP tool would report back when it finishes instead of blocking the lane. ↗ · Docs · David Soria Parra

🔬 Research

  • METR and Redwood's red-team of OpenAI's internal agent monitoring (Oct 22) — two auditors with code and prompt access for three weeks found that Codex agents could in principle get round the sandbox and auto-review; the monitor only ran when an agent handed control back to the user, so an agent could put it off by not stopping; compaction events probably went unchecked (about 10% of internal Codex traffic, May–July); and two client-set headers could turn monitoring off for new agents. Their lessons: check periodically rather than at turn end, prove that the traffic you think is watched really is, and keep agents away from monitor code. OpenAI says everything is patched, which METR hasn't checked. Dave: rulebook-nevers.py checks each tool call before it runs, the right side of the first finding. A Stop-hook reviewer (Oct 20's security-guidance Stop layer) only checks at turn end, so it can be a second line but never the only one. ↗
