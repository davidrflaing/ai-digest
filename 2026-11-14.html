  • [skill] Claude Code 2.1.325 (changelog, Nov 13; no 2.1.324 on the page) — a large release (about 47 changes, 88 fixes), and several of them make a session ask where it used to run. (1) "Changed scheduled tasks and /loop to ask before running a skill that declares allowed-tools or hooks; add Skill(name) to permissions.allow to run it unattended". (2) "Changed read-only git commands to ask first in a repository that isn't the project's or one you trusted; name it with --add-dir, not the additionalDirectories setting, to run them without prompts". (3) "Changed sandboxed Bash commands to follow the normal permission flow by default; set sandbox.autoAllowBashIfSandboxed: true to keep running them without prompts". (4) "Changed nested skill loading: .claude/skills folders in --plugin-dir plugins no longer load from a session started above them". (5) "Improved the account email check: it now also refuses your email as a client's identity in scripts a command runs, file writes, web fetches and MCP calls". Fixes worth knowing: "Fixed a gap in Bash permission checks where some compound commands could run without asking", "Fixed a case where a Bash allow rule could run a different program than the one it names", "Fixed a case where a committed .claude/settings.local.json could be treated as the user's own when Claude Code was started in certain subfolders of a repository", "Fixed a slash command's allowed-tools grants applying to background agents woken during or after its turn", and subagents cut off at the output limit "are now asked for the whole answer again, more briefly, instead of returning only its end". Flags: the entry doesn't say whether "scheduled tasks" covers a launchd job that calls claude -p, or only Claude Code's own scheduler; the Windows, VS Code and telemetry bullets were left out of this read. Dave: three checks. Lanes that run git status or git log in a repo other than their own (every cross-project session) may now stop and ask, so watch for stalls in the 🎯 Orchestrator's lanes and in the nightly comms pass. Any /loop or scheduled task that runs one of your skills with allowed-tools or hooks will now wait for you; whether to add a Skill(name) allow rule for it is your call, one skill at a time. And watch the widened email check on the Gmail-draft and commit steps, since the 2.1.321 fix was about that same check stopping scheduled runs. ↗
