Claude skills / plugins / MCP

  • [skill] Claude Code's "Don't ask again" saves secrets into .claude/settings.local.json (Apiiro, Nov 5; HN 434 / 293, front page yesterday and today) — when you pick "Yes, and don't ask again", Claude Code saves the approved command word for word as an allow rule. If the command had a password or token in it, the secret goes into the file too. Apiiro found 1,122 of 104,185 public copies of that file on GitHub holding a real secret (1,379 distinct secrets). Counting git history, shared settings.json files and agent transcripts, the total was 2,539 secrets across 1,994 public repos. The leaks were database passwords, cloud keys, API tokens and SSH root logins, and 211 forks carried the same secrets. bcherny (Claude Code team) replied on HN: ".claude/settings.local.json is meant to stay local… We automatically gitignore it when Claude creates the file, so in this case the files were manually created and checked in." He added: "Historically Claude Code has not done secret scrubbing… but we are looking into what we can do to prevent this." The docs say that on first write it adds **/.claude/settings.local.json to your global git excludes file. Flags: Apiiro's page refused this run (403), so the numbers come from coverage (iTWire, RuntimeWire, LetsDataScience) and the HN thread; Apiiro sells agent-security products; a global exclude doesn't protect a file git already tracks, a committed project settings.json, or a key sitting in a transcript; the article's author says on HN the ignore never reaches the repo's own .gitignore (others dispute it). Dave: three steps, all read-only, and none of them print a key. First, list which settings files hold a token-shaped allow rule, file names only: grep -l -E 'pit-[0-9a-f]{8}|ntn_[A-Za-z0-9]{20}|secret_[A-Za-z0-9]{20}|sk-(ant|proj)-|ghp_[A-Za-z0-9]{20}|EAA[A-Za-z0-9]{20}|Bearer [A-Za-z0-9._-]{20}' ~/.claude/settings*.json ~/*/.claude/settings*.json. Those patterns are GHL private tokens, Notion, Anthropic/OpenAI, GitHub, Meta, and any bearer header. Second, in each repo with a GitHub remote (the portal, the app, the plugin repos), run git ls-files .claude. If settings.local.json shows up, rotate the key first, then git rm --cached it. Third, add a line to checks-to-build.md: each night, flag any allow rule holding a token-shaped string, next to the Nov 4 settings diff. Run the same grep before a repo's first public push, at the same moment as commit-rewriter. ↗ · HN · 2nd source
  • [skill] Claude Code cloud sessions now set up their own environment, and keys go in as "network secrets" (ClaudeDevs, Nov 6; 5.1K engagement per AINews) — "Claude figures out what dependencies, network access, and API keys it needs, then saves the environment for next time. API keys are saved securely, so Claude never sees them." This covers Pro, Max and Ultra. The docs describe a network secret as "an API key or token you store on a cloud environment so Claude can call that API from any session in the environment without seeing the key". You list the API's hosts and the header that carries the key, and the network proxy adds it to each request. If setup finishes in about five minutes, Anthropic snapshots the filesystem, so later sessions start with dependencies already installed. Flags: the docs contradict each other: the "Claude Code on the web" page still says cloud environments have "no dedicated secrets store, so don't add API keys"; this run read the docs through search snippets, not the full pages; the API must accept connections from the internet; network secrets can't be used with customer-managed encryption keys. Dave: this is the answer to the item above for anything that runs in the cloud. A key the session never holds can't land in an allow rule or a transcript, and can't be lifted by a model either (see MaxxBench below). Use it if a launchd job (the digest's Notion and Telegram posts, consider-this) ever moves to a /schedule cloud routine. Storing a key with Anthropic goes by the rulebook's mark. No lane that touches client data runs in the cloud. ↗ · docs

GitHub repos & OSS tools

  • [repo] rea-video (JuneYaooo/rea-video; Apache-2.0; 3.9k★, +474 this week on Trendshift; 69 commits) — "Reverse-engineer any video, shot by shot: filmed, AI-generated or coded, and how to remake it." It "doesn't render a video". It returns a one-line read (its example: "41% AI video + 59% code UI, 8 s of real screen recording, library music at 122 BPM"). It writes a remake plan "split into what to film, what to generate and what to code", and a report.html with frames, camera and lighting notes and an audio breakdown for each shot. Caption timing exports to SRT or ASS. It needs ffmpeg and Python 3.10+. Tools-only mode is "offline and free"; a video model (Gemini or Doubao, your key) is optional. Flags: "The docs are in Chinese for now" (the example reports are in English); local files only, so download first; install_skill.sh links the skill into ~/.claude, ~/.codex and ~/.agents in one go; the accuracy figures are the maker's own (88.6% tools-only on re-encoded video, 99.6% with a vision model); telemetry isn't mentioned; the README says it's for learning structure, not reposting others' footage. Dave: this gives ad-creative-engine a structure read. Download one of your best-performing reels and one competitor reel.
